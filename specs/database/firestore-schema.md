# Firestore Schema

This document defines the canonical high-level Cloud Firestore schema for vucdem.

More detailed field definitions are defined in the individual files under:

```text
specs/database/
```

---

# 1. Database

vucdem uses:

```text
Cloud Firestore
```

Cloud Firestore is the canonical application database.

Do not use:

```text
Firebase Realtime Database
Firebase Storage
```

for application data or media.

Media files are stored in Cloudinary.

---

# 2. Core Collections

The primary Firestore collections are:

```text
users/
posts/
stories/
comments/
communities/
notifications/
conversations/
discussionMessages/
reports/
```

Additional utility collections may exist where required for uniqueness or trusted coordination.

Examples:

```text
usernames/
storySlugs/
```

These collections must be documented before implementation.

# 4. Canonical Identity

Firebase Authentication UID is the canonical User identity.

User documents use:

```text
users/{uid}
```

where:

```text
uid = Firebase Authentication UID
```

Do not generate a separate application User ID.

---

# 5. Document IDs

## User

```text
users/{uid}
```

Document ID:

```text
Firebase Authentication UID
```

---

## Post

```text
posts/{postId}
```

`postId` should normally be generated by Firestore before media upload or final publication so it can be used in Cloudinary paths.

---

## Story

```text
stories/{storyId}
```

`storyId` should normally be generated before cover upload.

---

## Chapter

```text
stories/{storyId}/chapters/{chapterId}
```

Chapter identity is scoped to its Story.

---

## Comment

```text
comments/{commentId}
```

Comments are stored in a root collection.

---

## Community

```text
communities/{communityId}
```

---

## Notification

```text
notifications/{notificationId}
```

---

## Report

```text
reports/{reportId}
```

```text
users/{uid}
```

- Public profile

- Profile metadata
- Denormalized counters
- Account application state

Detailed schema:

```text
specs/database/users.md
```

# 7. Posts Collection

Canonical path:

```text
posts/{postId}
```

Stores standalone community content.

Detailed schema:

```text
specs/database/posts.md
```

Votes are stored under:

```text
posts/{postId}/votes/{uid}
```

Do not embed all voters inside the Post document.

---

# 8. Stories Collection

Canonical path:

```text
stories/{storyId}
```

Stores Story-level metadata.

Detailed schema:

```text
specs/database/stories.md
```

Chapter content is stored under:

```text
stories/{storyId}/chapters/{chapterId}
```

Do not embed all Chapters in the Story document.

---

# 9. Comments Collection

Canonical path:

```text
comments/{commentId}
```

Comments reference their target through fields such as:

```text
contentType
contentId
```

Replies reference another Comment through:

```text
parentId
```

Do not create a separate `replies` collection.

---

# 10. Communities Collection

Canonical path:

```text
communities/{communityId}
```

Stores Community metadata.

A Post may reference a Community using:

```text
communityId
```

Community documents must not contain unbounded arrays of Post IDs or member IDs.

---

# 11. Notifications Collection

Canonical path:

```text
notifications/{notificationId}
```

Notifications are recipient-owned activity records.

Each Notification contains a recipient identifier such as:

```text
userId
```

Notifications are not the source of truth for the underlying event.

---

# 12. Reports Collection

Canonical path:

```text
reports/{reportId}
```

Reports reference a moderation target.

Supported target types are defined by the reports specification.

---

# 13. Username Reservation

Usernames must be unique if used in profile URLs.

Firestore cannot safely guarantee uniqueness through a simple query followed by a write.

Use a reservation document:

```text
usernames/{normalizedUsername}
```

Example:

```json
{
	"uid": "firebase-user-uid",
	"username": "nocturne",
	"createdAt": "Timestamp"
}
```

Creation or username changes must use a transaction or another trusted atomic mechanism.

---

# 14. Story Slug Reservation

Story slugs should be unique when used as:

```text
/story/{slug}
```

Use:

```text
storySlugs/{slug}
```

Example:

```json
{
	"storyId": "story123",
	"createdAt": "Timestamp"
}
```

Slug reservation and Story creation must be logically consistent.

---

# 15. Cloudinary Assets

Firestore stores Cloudinary references.

Canonical asset shape:

```typescript
type CloudinaryAsset = {
	url: string;
	publicId: string;
};
```

Example:

```json
{
	"url": "https://res.cloudinary.com/example/image/upload/vucdem/posts/post123/cover.webp",
	"publicId": "vucdem/posts/post123/cover"
}
```

Do not store:

- Binary image data
- Base64 images
- Cloudinary secrets

inside Firestore.

---

# 16. Firestore Timestamp

Canonical timestamp fields use Firestore Timestamp.

Common fields:

```text
createdAt
updatedAt
publishedAt
```

Trusted timestamps should use Firestore server-generated time where appropriate.

Do not use client-provided time as authoritative creation time.

---

# 17. Denormalization

Firestore documents may intentionally contain duplicated display information to reduce reads.

Examples:

```text
authorName
authorUsername
authorAvatarUrl
```

These fields are denormalized snapshots.

Canonical identity remains:

```text
authorId
```

Denormalization must be intentional and documented.

---

# 18. Counters

Primary documents may store denormalized counters.

Examples:

```text
voteScore
commentCount
viewCount
followerCount
followersCount
followingCount
postCount
storyCount
chapterCount
memberCount
```

Counters exist for:

- Efficient rendering
- Sorting
- Ranking
- Reducing reads

Clients must not have permission to arbitrarily set trusted counters.

---

# 19. Unbounded Relationships

Do not store unbounded relationships as arrays.

Avoid:

```json
{
	"followers": ["uid1", "uid2", "..."]
}
```

Avoid:

```json
{
	"comments": ["comment1", "comment2", "..."]
}
```

Avoid:

```json
{
	"chapters": ["chapter1", "chapter2", "..."]
}
```

Use subcollections or root collections.

---

# 20. Status Fields

Content documents should use explicit status fields.

Typical values:

```text
draft
published
hidden
removed
```

Exact allowed values are defined per content type.

Public Feed queries must only expose content allowed by the relevant status and security rules.

---

# 21. Logical Deletion

Content removal does not always mean physical document deletion.

Possible lifecycle:

```text
draft
   ↓
published
   ↓
hidden
   ↓
removed
```

Physical deletion should be implemented only when appropriate.

Do not implement uncontrolled cascading deletes.

---

# 22. Query Design

Firestore schemas must be designed around application queries.

Common Post queries include:

```text
published Posts ordered by createdAt
published Posts ordered by voteScore
published Posts in a Community
published Posts in a Category
Posts by authorId
```

Common Story queries include:

```text
published Stories ordered by updatedAt
Stories by authorId
Stories by slug
Stories ordered by followerCount
```

Required composite indexes must be documented in:

```text
specs/database/indexes.md
```

and represented in:

```text
firestore.indexes.json
```

---

# 23. Pagination

Large lists use cursor pagination.

Example:

```text
orderBy(createdAt, desc)
limit(20)
```

Next page:

```text
startAfter(lastDocument)
limit(20)
```

Do not use offset pagination for normal Firestore feeds.

---

# 24. Security

Every client-accessible collection must have matching Firestore Security Rules.

Rules must consider:

- Authentication
- Ownership
- Role
- Current state
- New state
- Fields being modified

Security specifications are defined under:

```text
specs/security/
```

---

# 25. Firestore Rules Are Not Filters

Queries must satisfy Security Rule constraints.

If public access requires:

```text
status == "published"
```

a public list query should normally also constrain:

```text
status == "published"
```

Do not query private and public documents together and expect Security Rules to filter the response.

---

# 26. TypeScript Models

Application TypeScript types must remain aligned with Firestore specifications.

Canonical types live under:

```text
src/lib/types/
```

Examples:

```text
user.ts
post.ts
story.ts
comment.ts
community.ts
```

Do not maintain conflicting copies of the same domain model.

---

# 27. Schema Change Rule

Before introducing:

- A new collection
- A new subcollection
- A new canonical field
- A new enum value
- A new relationship
- A new trusted counter

update the appropriate file under:

```text
specs/database/
```

Do not silently let implementation diverge from these specifications.

Detailed schemas take precedence:

```text
users.md

stories.md
chapters.md
comments.md
votes.md
```
